# GDataHub データ取得手順書（画面開発向け）

> 調査結果・暫定実装方針。**正式な外部公開API仕様書ではありません。**

## 1. 結論と適用範囲

既存intra-martのテーブル管理画面では、POSTの内部RPC `getData` によりテーブルデータを取得する通信を観測しました。複数画面で通信形式が共通しており、画面開発における取得処理の共通化を検討できます。

**通信確認済みは4テーブルのみです。**

別画面／ブラウザ拡張機能からの直接呼び出し、認証・セッション管理、公式サポート範囲は未検証です。この資料の記載だけで、内部RPCを正式な連携APIとして採用しないでください。

## 2. 位置づけ

| 区分 | 確認結果 |
| --- | --- |
| 既存画面 | intra-martテーブル管理画面の `getData` 通信 |
| API構想 | 提供された「Api機能目的.txt」では、他システムから直接参照・登録・更新するAPIは未整備と記載 |
| 画面開発からの利用 | 正式な連携方式・認証・許可範囲は未決定／未検証 |

既存の機械情報検索画面の**CSV出力連携**は [GDH_INTEGRATION.md](../GDH_INTEGRATION.md) を参照してください。`getData` の内部RPCとCSV出力は別の方式です。

## 3. 調査対象

| 対象 | テーブル名 | 確認内容 |
| --- | --- | --- |
| オーダー情報 | `ZALDTB_ORDER_INFO` | 空の `data` 配列、画面表示0件 |
| 契約情報 | `ZGDDTB_CONTRACT_INFO` | 100件のResponse、19項目 |
| 販売情報 | `ZGDDTB_SALES_INFO` | 100件のResponse、16項目 |
| 顧客マスタ | `ZGDDTM_CUSTOMER` | 100件のResponse、18項目 |

項目名の一覧は [ZALS_TABLE_COLUMNS.md](ZALS_TABLE_COLUMNS.md) にまとめています（16テーブル・264項目）。**16テーブルすべての通信を検証したわけではありません。**

## 4. 処理の流れ

1. 利用者が既存画面で対象テーブル、検索条件、表示ページを指定
2. 画面が `getData` をPOSTで呼び出し
3. Responseの `data` 配列にレコードが格納される例を確認
4. 新規画面では（承認・検証後に）必要な項目のみを安全に表示する設計を検討

## 5. 確認済みの通信仕様

| 分類 | 観測値 |
| --- | --- |
| HTTPメソッド | `POST` |
| 相対パス | `/cncservice/tablemaintenance(2f)views(2f)table(5f)edit.jssprpc` |
| URLパラメータ | `im_func=getData`、`im_from=tablemaintenance(2f)views(2f)table(5f)edit`、`im_mark` |
| Content-Type | `application/json; charset=UTF-8` |
| 通信条件 | same-origin、既存ログインセッションのCookieを含むリクエスト |

社内ホスト名、Cookie、実際の `im_mark` 値は記録しません。`im_mark` の意味・取得方法・有効期間は不明です。既存画面内のページ移動では同値でしたが、画面変更に伴う値の違いは観測しています。

## 6. Request Payload の主要項目

| 項目 | 観測値／判断 |
| --- | --- |
| `db_source` | `ZALS` |
| `tablename` | 対象テーブルの物理名 |
| `pagenumber` | 画面ページと対応。契約情報で `2` → `3` を確認 |
| `pageline` | `100`。画面の100件表示に対応 |
| `searches` | `tm_seach_fieldname__<列名>` 形式のキー。列はテーブルごとに異なる |
| `page` / `rowNum` | `1` / `50`。役割は未確定（ページ移動時も同値） |
| その他 | `keyword`、`sortOrder`、`sortName`、`order` など |

元のPayloadは1要素の配列として提示されました。以下は**構造だけを示す省略例であり、そのまま送信できる完全なリクエストではありません**。

```json
[
  {
    "db_source": "ZALS",
    "tablename": "ZGDDTM_CUSTOMER",
    "pagenumber": "1",
    "pageline": "100",
    "searches": {
      "tm_seach_fieldname__customer_id": ""
    }
  }
]
```

実際のPayload表示では `isphysicalname: undefined` など標準JSONで表現できない部分も確認しています。送信ボディを構築する前に、実際のワイヤ形式とintra-mart側のシリアライズ／復元方法を確認してください。

## 7. Responseの読み取り

| キー | 観測内容／利用方針 |
| --- | --- |
| `data` | レコードの配列。新規画面で利用する候補 |
| `trarray` | HTML文字列の配列。画面依存のため直接再利用しない |
| `sizedata` | 配列。用途は不明 |
| `selecteddata` | 提示形式では `undefined` |
| `error` | 正常取得例では `false` |

`data` にも `undefined` が観測される場合があり、提示テキストをそのまま `JSON.parse` できるとは限りません。実際の生Response・データ型・空値の扱いを確認し、実データを使ったHTML文字列挿入は避けてください。

## 8. 開発者ツールによる既存通信の確認

1. 権限のあるintra-martテーブル管理画面を開く
2. 開発者ツール → Network → Fetch/XHR
3. ページ番号を切り替え、`getData` の通信を選択
4. Headers：メソッドと通信先、Payload：テーブル名／ページ番号、Response：`data`／`error` を確認
5. 秘密情報・顧客情報などの**実値は転記せず**、構造情報のみ記録

## 9. 新規画面への適用（提案・未検証）

- 承認された公式APIが利用可能な場合はそちらを優先
- 内部RPCを採用する前に利用許可、サポート範囲、セッションおよび `im_mark` の扱いを確認
- 最初は許可された1テーブル・1ページ（100件）で読み取り専用の検証
- レコードの表示には `data` を検討し、テーブルごとの列差異を吸収
- `pagenumber` を用いたページ切り替えを実データで再確認
- 大量一括取得を避け、件数上限・監査要件に従う

## 10. 実装前に確認が必要な事項

| 重要度 | 未確認事項 |
| --- | --- |
| 必須 | 正式な外部公開APIの有無、利用許可、仕様 |
| 必須 | 別画面・拡張機能からの通信可否と利用権限 |
| 必須 | `im_mark` の生成／更新／失効とセッション管理 |
| 必須 | 実際のリクエスト本文の厳密な形式、`undefined` の扱い |
| 必須 | エラー形式、タイムアウト、取得件数・通信制限 |
| 後続 | 検索条件／ソートの動作、テーブル／列情報の取得方法 |

Cookie、SSOトークン、実際の `im_mark`、顧客情報、契約情報、機密ログをソースコードやGitHubに保存しないでください。権限を越えた取得や不要な一括取得は行いません。

## 11. 根拠・確認範囲

ユーザーが共有したNetworkのHeaders／Payload、契約情報・販売情報・顧客マスタのResponse、オーダー情報の空Response、「Api機能目的.txt」に基づく調査結果です。項目一覧は追加のMarkdown提供資料を基に転記しました。

**社内サイトへの直接アクセス、API実行、拡張機能からの本番動作試験は実施していません。**
